# SEED2 : jeu d'amorçage H2 par contexte propriétaire

## Constat avant code
- `seed.sql` : 2 443 l., 142 Ko, mélange 11 propriétaires, entrelacés (référentiels du centre 1, puis identité, puis documents, puis référentiels du centre 2, puis patients...). Il contient aussi du DDL (`CREATE TABLE IF NOT EXISTS releves_per_seance, medicaments_seance, prescriptions_medicales, autres_traitements_prescription, resultats_analyses, articles_consommes_seance`, 43 `ALTER TABLE volet_paramedical`) et des `INSERT ... SELECT` à `RANDOM_UUID()` / `ROW_NUMBER()` qui dépendent de l'ordre des lignes déjà présentes (d'où la règle « même ordre relatif par propriétaire »).
- Non déterminisme du jeu (donc pas d'empreinte figée possible) : `CURRENT_DATE`/`CURRENT_TIMESTAMP` (99 occurrences), `RANDOM_UUID()` (attestation_droit, prise_en_charge), hachage des mots de passe (SeedPasswordInitializer), licences de développement (DevLicenseBootstrapInitializer), modèles de documents provisionnés (ModeleDocumentProvisioner).
- Aucune clé étrangère de données hors identité -> `app_user_center` -> `centers` : l'ordre ne compte que là et pour les `SELECT` croisés.

## Livré (tranche 1)
Fichiers de production : `contexts/organisation/.../db/h2/organisation-seed.sql` (sociétés, centres, calendrier, médecins, salles, créneaux des deux centres), `contexts/gmao/.../db/h2/gmao-seed.sql` (5 générateurs), `contexts/documents/.../db/h2/documents-seed.sql` (16 modèles) ; `db/seed.sql` réduit (blocs retirés, commentaire de renvoi) ; `application.yml` et `application-demo-renadial.yml` (même liste ordonnée, RENADIAL en dernier) ; `AGENTS.md`, ADR 0188, `seance-se7e-pg16-rejeu.sh` (fenêtre de ligne).
Ordre : organisation, `db/seed.sql`, gmao, documents, comptabilité.
Tests : `SeedH2DesScriptsParContexteTest` (permanent, voir ADR 0188 pt 4) ; vert sur l'ancien script AVANT toute découpe (preuve que le test et ses normalisations tiennent), vert après.

## Parité : preuve

Deux contextes complets, deux bases ; empreinte par table (comptage + lignes triées + SHA-256) et colonnes de toutes les tables. Normalisations nommées dans le test (COLONNES_ALEATOIRES). Aucun golden touché, `Schema*` vert (référence de schéma inchangée), `Table*Test` et gardes d'architecture verts sans modification.

## RENADIAL : générateur et découpe (NON faite)
- Générateur : `backend/platform/src/main/resources/db/demo/generate-renadial-seed.cjs` (Node, sans dépendance ; `node ...generate-renadial-seed.cjs` écrit `renadial-seed.sql` à côté, 5,7 Mo). PRNG déterministe (graine 42) MAIS identifiants par `crypto.randomUUID()` (aléatoires à chaque exécution) et fenêtre de 12 mois calculée sur la date du jour : deux générations ne donnent jamais le même fichier -> aucune parité octet/empreinte possible, uniquement des comptages (DemoRenadialProfileValidationTest : 1 société, 17 centres, > 400 patients). `renadial-purge.sql` est écrit à la main (2,8 Ko), par société.
- Sortie unique : tout passe par `insert(table, cols, rows)` dans un tableau `out` écrit en une fois (l. 413). 15 tables : societes, centers (organisation) ; caisse_assurance, agence, centre_payeur, patients (patient-couverture) ; seances (séance) ; factures, facture_reglements (facturation) ; resultats_analyses, serologies_patient, administrations_anemie, alertes_observance, bilans_pre_greffe (dossier médical) ; articles, lots (stock).
- Ce qu'il faudrait : (1) une table de propriétaires dans le générateur et un `out[proprietaire]` (insert() aiguille par table ; les quelques `out.push` bruts doivent suivre leur table) ; (2) une écriture par propriétaire dans `contexts/<ctx>/src/main/resources/db/demo/renadial-<ctx>-seed.sql` (jars de 0,2 à 3 Mo chacun : à chiffrer, ils alourdissent des jars de production alors que le jeu n'est que démo) ; (3) la liste de `application-demo-renadial.yml` ordonnée organisation, patient-couverture, séance, facturation, dossier médical, stock (aucune FK ; les identifiants sont des variables du générateur donc cohérents entre fichiers d'une même génération) ; (4) `renadial-purge.sql` à répartir de même ; (5) RÉGÉNÉRER (c'est le seul moyen de produire les fichiers ; interdit à la main) puis rejouer `DemoRenadialProfileValidationTest` ; (6) retirer les entrées `renadial-seed.sql`/`renadial-purge.sql` des gardes (`TableDesSeancesTest`, `TableDesAnalysesTest`, `TableDuDossierMedicalTest`) au profit de l'exclusion du module propriétaire. Décision à prendre avant : accepter que le jeu de démo vive dans les jars de production, ou le sortir dans un module `demo` dédié (alors les gardes le balayent comme aujourd'hui).
- Non fait ici : le critère « le générateur le permet proprement » est rempli techniquement, mais la régénération change 5,7 Mo de données de démonstration et n'a aucune parité vérifiable : à valider par l'utilisateur.

Parité verte à chaque tranche (SeedH2DesScriptsParContexteTest + package architecture, 202 tests).
`db/seed.sql` final = identité + JEU DÉRIVÉ MULTI-CONTEXTES (séances, volets, relevés, médicaments, prescriptions, analyses, consommables, 2 `INSERT bons_sortie`, factures, lignes, `UPDATE seances.facture_id`), soit tous les `INSERT ... SELECT` qui lisent patients/séances/factures.
ARRÊT PROPRE, pas d'obstacle de données : c'est une contrainte de garde. Un script de contexte qui lirait `patients` (séances), `seances` (volets, bons de sortie, factures), etc. serait un nouveau lecteur SQL pour `TableDuPatientCouvertureTest`/`TableDesSeancesTest`/`TableDuDossierMedicalTest`/`TableDuStock...` : il faudrait l'inscrire avec un butoir, donc reporter. Les entrées `db/seed.sql` de ces gardes restent, butoir 2027-06-30, non reportées. Pour les solder : (a) supprimer le jeu dérivé de la démonstration (garder le seul jeu RENADIAL ou un jeu minimal), ou (b) le réécrire sans lecture inter-contextes (formules d'identifiants, dates et statuts fixes ; perte de la parité stricte). Décision utilisateur.
