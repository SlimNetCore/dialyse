# Filet de caractérisation — G6 consultation et pilotage de la GMAO (refonte sur place)

Lectures seules : aucune ne modifie un agrégat, mais le bon PDF écrit une ligne de paramétrage (KB-GMAO-70). Ces lectures lisent des tables `gmao_*` désormais **écrites par le nouveau module** (`contexts/gmao`, G1 à G5) à travers des classes **legacy** (`bc-gmao`, adaptateurs/entités JPA de `platform`) : le filet décrit ce que ces lectures renvoient aujourd'hui sur des données semées par SQL **et** produites par les routes du nouveau module.

## Point d'observation et harnais
HTTP via MockMvc sur le contexte Spring complet (`@SpringBootTest` MOCK, profil `test`, Spring Security et `RoleScopeFilter` réels, JPA réel sur **H2**) ; lecture SQL des tables seulement pour la cohérence. Harnais réutilisé : `GoldenMaster` (G1), mêmes conventions que G4/G5 (alias d'ids, goldens `*.approved.json`, approbation `-DargLine=-Dcharacterization.approve=true`, attente du registre d'événements Modulith vide). Nouveau : `PilotageCharacterizationSupport` (identités ADMIN/DIRECTION/rôles seuls, fixtures SQL à valeurs maîtrisées, extraction du texte PDF par PDFBox déjà présent via `openhtmltopdf`). **Aucun mock du code caractérisé, aucun seam, aucun code de production modifié.**
- Tests : `backend/platform/src/test/java/com/hemodialyse/backend/characterization/gmao/pilotage/` : `BonPdfCharacterizationIntegrationTest` (16), `IndicateursChronologieCharacterizationIntegrationTest` (14), `FicheEquipementCharacterizationIntegrationTest` (13), `StatsGmaoCharacterizationIntegrationTest` (5), `DirectionGmaoCharacterizationIntegrationTest` (11) = **59 tests**.
- Goldens : `backend/platform/src/test/resources/characterization/gmao/pilotage/*.approved.json` (44 fichiers ; les matrices ont une ligne de texte par cas).
- **PDF sans seam** : le contenu binaire n'est pas stable (métadonnées, horodatage d'édition) ; on observe donc le type, `Content-Disposition`, la signature `%PDF-`, le nombre de pages et le **texte extrait** (PDFBox), dont seul « Édité le jj/mm/aaaa hh:mm » est masqué. Les montants, dates (fuseau), libellés, lignes de coût et chronologie du bon sont ainsi verrouillés.

## Mesures
- **Suite** : 3 exécutions consécutives vertes, 59/59 (la 1ʳᵉ en ordre par défaut, les 2 autres en ordre `MethodOrderer$Random`), 0 flaky. Durée : ~45 s par exécution, dont ~40 s de démarrage Spring et de compilation Jasper du bon.
- **Mutation PIT 1.30.0** (`backend/scripts/pit-g6-calculs.sh`, `TESTS=filet`) sur les trois services de domaine de calcul lus par G6 (`IndisponibiliteCalculator`, `AideDecisionMaintenance`, `IndicateursIntervention`) **par le seul filet HTTP** : **49 mutants, 36 tués (73 %)**, force des tests 77 %, couverture de lignes de la zone 56/62 (90 %). Les 13 survivants sont tous **équivalents ou injoignables par HTTP** : gardes `from/to == null` et période vide de `IndisponibiliteCalculator.calculer` (L48-49, appelant toujours valide), `isAfter(to)` après le `break` (L58, L83-84 : code mort, résultat identique), `total.isNegative()` (L68, jamais négatif), `statut == null` (L72, `EnumSet.contains(null)` vaut déjà faux), garde du seuil du constructeur de `AideDecisionMaintenance` (L18 : seuil non positif = contexte qui ne démarre pas) et valeurs `null` de cumul/période (L33-34 : les adaptateurs renvoient `0`). Aucun mutant de `IndicateursIntervention` ne survit. Avec les tests unitaires de `bc-gmao` seuls (`TESTS=unitaires`) : 38/49 (78 %), mêmes survivants. Cible ≥ 70 % atteinte ; la parité à 100 % des mutants joignables est donc acquise.
- **Couverture de branches** : JaCoCo n'est pas configuré dans le projet (comme G1 à G5) ; la couverture de lignes de la zone de calcul est mesurée par PIT ; les 6 routes, les 3 sorties du bon (`PDF`, `EXCEL/XLS/XLSX`, `HTML`), `zone()`, les 3 priorités, les 6 types d'événement de la chronologie, tous les statuts d'équipement et d'intervention, et chaque branche d'erreur des contrôleurs sont exercés par un scénario nommé.

## Bugs connus
KB-GMAO-69 à 79 (`known-bugs.md`) : suppression logique non filtrée à la lecture par id, GET qui écrit (modèle de document), fiche non filtrée par centre, ratio arrondi avant comparaison au seuil, « Désactivé » disponible pour un patient, défauts du bon PDF (fuseau « Z », page 2, éditeur = identifiant, main d'œuvre vs honoraires), codes d'erreur de lecture (400/403/500), échelle des nombres JSON hétérogène, statistiques (total ≠ somme), pilotage direction (extras non triés, N+1), indicateurs/chronologie (MODIFIEE parasite, plafond à 100 %).

## Non verrouillé (limites)
- **Bon personnalisé** : la version personnalisée du centre (`modele_document` + version JRXML compilée à la volée, `CustomTemplateCompiler`) et le logo/identité société complets (seul le nom de société et de centre est semé) ne sont pas exercés ; le rendu **visuel** (mise en page, polices) n'est pas verrouillé, seulement le texte extrait ; PDF octet par octet non comparé (métadonnées instables).
- **Fuseau du serveur** : le texte « Édité le » est converti dans le fuseau demandé ; la valeur exacte est masquée.
- **Performance** : p95, N+1 de `DirectionGmaoQueryService` (un historique par équipement), chargement en mémoire des plans en retard : non mesurés (H2, petits jeux).
- **PostgreSQL** : comportement du SGBD (arrondis de `SUM`, échelle des `NUMERIC`, `TIMESTAMP WITH TIME ZONE`, ordre non spécifié sans `ORDER BY`) non testé ; la colonne `taches_a_effectuer` (PostgreSQL, V5) s'appelle `tachesaeffectuer` dans le schéma H2 généré par Hibernate : le filet sème par SQL sur le nom H2.
- **Concurrence** : aucune lecture n'est transactionnelle sur plusieurs tables (une écriture concurrente entre deux lectures de la fiche peut donner une fiche incohérente) : non testé.
- **Périodes lointaines** : `DirectionCapaciteQueryService` hors comptage des générateurs (file active, séries, niveau, masquage d'anonymat) : couvert par `DirectionCapaciteIntegrationTest`, pas ici.
- **Autres lecteurs SQL de `gmao_equipements`/`gmao_interventions`** (planification, optimisation, séance, patient, salle, référentiel, mouvements) : non G6, non rejoués ici.
- **Front** (`gmao-api.service.ts`, écrans) : non observé (e2e à la charge de l'utilisateur).
- **Instants dépendant de l'exécution** : durée d'une intervention en cours, panne ouverte jusqu'à maintenant, fenêtre de 12 mois (encadrés à ±2 min, pas exacts).

## Questions de décision pour la conception sur place
1. **Où vit chaque lecture ?** Proposition à valider : fiche, disponibilité patient, indicateurs, chronologie, statistiques et données du bon deviennent des *read models* de `contexts/gmao` (ports de lecture comme `LectureInterventions`, mêmes URLs, mêmes tables) ; `IndisponibiliteCalculator`, `AideDecisionMaintenance` et `IndicateursIntervention` migrent comme services de domaine purs du module (seuil injecté) ; le **rendu** du bon (Jasper, `ModeleDocumentPrinter`, identité société/centre, formats) reste dans `platform` derrière un port du module (le moteur d'impression est partagé avec les autres documents).
2. **Pilotage direction** : migrer maintenant la **source** de `DirectionGmaoQueryService` (remplacer les ports legacy par une lecture publiée du module GMAO, par exemple un read model « synthèse GMAO du centre » dans `published-language`) tout en laissant service, endpoint, alertes et garde de société dans `platform` ; sinon `bc-gmao` ne peut pas disparaître. Ne **pas** extraire Pilotage direction maintenant (autre contexte du design stratégique).
3. **Corriger ou reproduire** : KB-GMAO-69 (suppression logique), 72 (arrondi avant comparaison), 73 (désactivé disponible), 74d (honoraires 0,00), 79 (MODIFIEE parasite) ; échelle JSON (KB-GMAO-76).
4. **Seuil de réforme** : global conservé (KB-GMAO-05) ou par centre ?
5. **Retrait de `bc-gmao`** : traiter `GenerateurIndisponibleService`, `GmaoEvenementsPlanificationListener` et `PatientMigrator` dans G6 ou dans une slice dédiée ?
6. **Seam d'horloge** : l'appliquer (accord requis) ou conserver l'encadrement de ±2 minutes ?
