## Points conformes (vérifiés)
- Domaine pur : aucune dépendance de framework. L'heure arrive en paramètre. Les changements d'état passent par des méthodes d'intention (`enregistrerExecution`, `suspendre`, `reprendre`), sans setter. Les 4 événements sont au passé. Petit agrégat, référencé par identité (`EquipementId`, `CentreId`). `FrequenceMaintenance` est une énumération immuable (`PlanMaintenance.java`, `FrequenceMaintenance.java`).
- Use cases sans règle métier : une transaction par agrégat. Événements publiés via le registre Modulith (outbox) et consommés après commit (`EtablirPlan.java:29-39`, `ProjectionPlanVersLegacy.java:28`).
- Mapping explicite entre persistance et domaine. Verrou optimiste via `version`.
- Composition root unique (`GmaoConfiguration`). Routes `/_strangler/**` accessibles seulement par FORWARD (`GardeForwardSeulement.java:16-20`).
- Flag **OFF par défaut** avec double garde : kill-switch puis mode de la tranche (`RoutageParProprietes.java:33-38`). En cas d'erreur, la façade retombe sur le legacy (`RoutageStranglerFilter.java:66-72`). Rattrapage désactivé par défaut.
- Pas de dual write par conception : rattrapage dans un sens, projection idempotente (état complet réécrit) dans l'autre, sous réserve de B2.
- Migrations additives : `CREATE … IF NOT EXISTS`, schéma `gmao` séparé, aucune modification de `public.*`.
- Bugs legacy tracés (KB-06, 11-21) avec une décision pour chacun. Aucun fichier legacy `src/main/java` modifié.

## Verdict : **fail** pour l'activation, aucune réserve pour l'état `built` inerte
Avec la configuration par défaut, le code livré n'a aucun effet (façade OFF). Le merge peut donc se faire sans risque. En revanche, **aucun palier ne doit être activé**, même un shadow avec forward, tant que B1 et B2 ne sont pas corrigés et que M2 n'est pas levé.

### Top 3 actions
1. **B1** : placer la façade après les filtres d'audit, de licence et de rôle (ou router au niveau du DispatcherServlet) et l'éprouver par un test sur la vraie chaîne de filtres.
2. **B2** : router les commandes selon le centre propriétaire du plan, et tester la parité avec une cohorte mixte.
3. **M2 + M3** : jouer V34/V35 et les contrats sur PG16 ; décider de `EquipementExiste` et alerter sur les publications incomplètes avant le shadow.
