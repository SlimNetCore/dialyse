# 0024 — Refactoring sur place de GMAO, abandon du Strangler progressif

## Contexte
Le Strangler progressif (façade de routage, table de routage par centre, projection nouveau vers legacy, rattrapage, réconciliation, gel d'écriture, bascule par paliers) avait été construit pour G1 et G2 sans jamais être déployé. Il représentait beaucoup de code et d'exploitation (double propriétaire des données, API d'exploitation, tests de parité) pour un bénéfice faible : l'application n'a pas besoin de bascule à chaud par centre.

## Décision
1. **Refactoring sur place** : les slices sont refaites dans le module `backend/contexts/gmao`, avec le **même stockage** (tables `gmao_plans_maintenance`, `gmao_intervenants`, mêmes noms de colonnes, y compris `tachesaeffectuer`, KB-GMAO-21) et les **mêmes URLs** (`/api/v1/gmao/plans-maintenance`, `/api/v1/gmao/intervenants`). Aucune migration de schéma pour G1 à G3 et G5 (la seule exception est la V36 additive des tâches d'intervention, voir l'amendement G4 temps 2), un seul propriétaire des données, livraison en une fois.
2. Les contrôleurs du module sont des `@RestController` normaux : ils passent par la chaîne de filtres existante (sécurité, licence, rôle, audit). Les contrôleurs, DTO de requête, et la version legacy de ces deux slices sont retirés pour ne pas avoir deux contrôleurs sur une même URL.
3. Le **filet de caractérisation** (35 scénarios G1, 39 scénarios G2, goldens) reste la référence : une seule suite par slice, qui tourne désormais contre le nouveau code. Plus de suite de parité séparée.
4. Écarts de comportement décidés (inchangés) : KB-GMAO-14 (équipement inconnu : 400 `EQUIPEMENT_INCONNU`), KB-GMAO-22 (`GET /intervenants/{id}` : 200 ou 404). Les autres bugs legacy sont reproduits (ADR 0019).
5. Supprimés : façade/routage, table de routage, API d'exploitation, gel, bascule, réconciliation, projection et suivi des échecs, rattrapage, migrations Flyway V34, V37, V38 et l'ANCIENNE V36 (projection, schéma `gmao`), jamais déployées. **Le numéro 36 a ensuite été réutilisé** par une migration toute différente, la V36 actuelle `V36__gmao_taches_intervention.sql` (tâches d'intervention, additive, ré-exécutable, amendement G4 temps 2) : une base de dev qui porte encore l'ancienne V36 se reconnaît à sa description (voir `.ddd/migration/verifications-production.md` §8), flag `hemodialyse.strangler.*`, réglage Hibernate global `create_namespaces`.
6. **Métriques** : retirées à la demande de l'utilisateur (port, adaptateur Micrometer, dépendance, tests). Aucune métrique n'est créée.
7. **Conservés** (ADR 0013 reste valide) : les événements de domaine publiés par `PlanMaintenance` et `Intervenant` (port `PublicateurDEvenements`), le registre Spring Modulith (`event_publication`, migration V35, `@EnableAsync`), avec un consommateur minimal `JournalDesEvenements` qui journalise et acquitte (sinon aucune publication n'est enregistrée ; une fois acquittée elle est supprimée, rien ne s'accumule). Les futurs consommateurs (Planification, Pilotage, Notifications, à partir de G3) s'abonnent à ces événements.

## Conséquences
- Code nettement plus simple : domaine pur, cas d'usage, adaptateurs JPA directs sur les tables existantes, contrôleurs, une configuration.
- Pas de retour arrière à chaud : le retour arrière est celui d'un déploiement (version précédente, mêmes tables, aucune donnée à rapatrier).
- La production historique doit porter la colonne `tachesaeffectuer` (KB-GMAO-21) ; à vérifier avant déploiement.
- Pas de contrôle de concurrence optimiste (les tables n'ont pas de colonne de version). **Verrou pessimiste sur l'intervention (G4, 2026-10-12)** : toute commande qui modifie une intervention (démarrer, terminer, annuler, rectifier, lignes de coût, tâches) la charge par `InterventionRepository.chargerPourModification` (`SELECT ... FOR UPDATE`, même mécanisme que le quota des pièces jointes G5), dans la transaction de la commande : deux commandes simultanées s'exécutent l'une après l'autre, plus de mise à jour perdue (clôture effacée par un ajout de tâche), limite de 30 tâches tenue. Interventions : verrou pessimiste ; plans, intervenants, équipements : pas de verrou, comme le legacy. Ordre des verrous inchangé : intervention puis équipement. Le legacy (non migré) n'écrit pas dans ces lignes avec ce verrou : seules les commandes du module sont sérialisées.

## Amendement G3 (2026-10-12)
- **G3 (équipements) est aussi refait sur place** : table `gmao_equipements` et historique des statuts inchangés, mêmes URLs `/api/v1/gmao/equipements`, GMAO propriétaire de la table (le port `EquipementExiste` de G1 lit désormais via `EquipementRepository`).
- **Alerte Planification** : un écouteur dans `platform` (`GmaoEvenementsPlanificationListener`) consomme `EquipementMisHorsService` et `EquipementReforme` et appelle `GenerateurIndisponibleService.signaler` (règle KB-GMAO-37 inchangée). Il ne gère pas le cache.
- **Cache `ref.generateurs`** : `@CacheEvict` **synchrone** sur les écritures d'`EquipementControleur` (même éviction que le legacy).
- **`EtatEquipementPort`** (publishedlanguage) : la clôture d'intervention legacy applique l'état constaté via le module ; contrat inchangé.
- **KB-GMAO-32** (écart décidé) : la réforme exige `ADMIN` et `GMAO_REFORME`. **KB-GMAO-38** (écart bénin) : équipement, historique et publication dans une seule transaction.
- Événements non versionnés (les événements de domaine sont les événements publiés), à versionner avec un 2e consommateur.
- **Revue (2026-10-12)** : KB-GMAO-15 corrigé pour les plans (décision utilisateur, voir ADR 0019 amendé) ; registre d'événements : dépendances `spring-modulith-events-*` à la place du starter (plus de `moments` ni `apt`), `schema-initialization.enabled=false` en profil `prod` (la table vient de V35), publication incomplète rejouée à la demande (test) ; rejeu PostgreSQL 16 étendu à G3.

## Amendement G4 temps 2 : nouvelles fonctionnalités (2026-10-12)
- **Hors refactoring, à la demande explicite de l'utilisateur** (KB-GMAO-55 et 57), donc sans filet de parité : (A) **tâches d'intervention** (entité interne de `Intervention`, table `gmao_taches_intervention` (créée vide par V5, jamais utilisée), migration **additive** Flyway V36 qui y ajoute les colonnes manquantes, trois routes sous `/api/v1/gmao/interventions/{id}/taches`, événements `TacheAjoutee`/`TacheDemarree`/`TacheAchevee` par l'outbox) ; (B) **proposition de réforme P2** : `platform` (`infrastructure/acl/gmao/GmaoEvenementsReformeListener`) consomme `EquipementMisHorsService` (statut `A_REFORMER`, cause intervention) et crée la notification durable `REFORME_PROPOSEE` pour le rôle `GMAO_REFORME` du centre ; le module GMAO ne dépend pas de `platform`.
- Le golden `taches_aucune_route` (comportement legacy d'absence) est **caduc** et remplacé par des goldens `*_nouveau_code` ; aucun autre golden n'a changé. Une assertion non-golden du test `terminer_en_proposant_la_reforme_…` (absence de notification de réforme) a été mise à jour.
- Conventions inchangées : ids inconnus 400, règle métier 422, `ADMIN` seulement, isolation de centre dès le départ. **À valider par le métier** : statuts et limite de 30, qui gère les tâches, texte et destinataires de la notification. Pas de façade, pas de flag (ADR 0024).

## Ce qui reste à faire
Des écrans legacy lisent encore les mêmes tables et ports (clôture d'intervention, fiche équipement, statistiques GMAO) : `Intervenant`, `TypeIntervenant`, `IntervenantRepositoryPort`, `PlanMaintenance`, `FrequenceMaintenance`, `StatutPlan`, `PlanMaintenanceRepositoryPort`, leurs adaptateurs, entités et dépôts JPA, et `PlanMaintenanceResponse` restent dans `bc-gmao` et `platform`. Ils seront retirés quand G4 (interventions) et G6 (consultation, pilotage) seront migrés. Le détail est dans les fiches des slices.

## Amendement G5 : pièces jointes d'intervention (2026-10-12)
- **Modèle** : `PieceJointe` est un agrégat satellite à une seule entité (son repository, ses événements), rangé à côté de `Intervention` pour ne jamais charger jusqu'à 5 Mo d'octets avec elle ; les listes passent par un read model qui ne lit pas la colonne `contenu`. Stockage inchangé par décision : **les octets restent en base** (`bytea`), même table `gmao_documents_intervention`, mêmes colonnes, aucune migration.
- **Intervention hôte** : les pièces lisent le centre, le statut et la suppression logique de l'intervention par le port `InterventionsHotes` (sans charger l'agrégat). `joindre` et `retirer` verrouillent la ligne de l'intervention (`SELECT ... FOR UPDATE`) le temps de la transaction : le quota de 50 est contrôlé et inséré sous verrou, un seul des deux envois simultanés au 50e emplacement passe (KB-GMAO-58).
- **Écarts décidés** (utilisateur, 2026-10-12, goldens `*_nouveau_code`) : KB-GMAO-59 (structure PDF/PNG/JPEG et extension cohérente), KB-GMAO-60 (nom assaini, `..`, U+202E, U+0085, troncature sans couper un emoji), KB-GMAO-61 (nom et type MIME re-contrôlés à la lecture, `application/octet-stream` pour un type hérité hors des trois formats), KB-GMAO-64 (ajout et retrait refusés sur une intervention annulée, terminée ou supprimée : 422), KB-GMAO-58 (quota réellement tenu). Reproduits : 500/400/403 transverses (KB-GMAO-62/63), audit POST/DELETE seul, ADMIN seul, 5 Mo exacts, doublons, suppression physique, plafonds du conteneur (KB-GMAO-65 à 68). Détail et impacts : `.ddd/safety-net/known-bugs.md`, « Décisions G5 ».
- **Événements nouveaux** `PieceJointeAjoutee` et `PieceJointeRetiree` par l'outbox (sans octets, sans consommateur). **Retiré** : le contrôleur legacy, la réponse, le domaine `DocumentIntervention`, `TypeDocumentIntervention`, le port, l'adaptateur, l'entité et le dépôt JPA (plus aucun lecteur ; le contrôle d'alignement des modèles compare désormais le modèle du module à la description figée de la table). Rien ne reste à retirer pour G5.

## Amendement G6 temps 1 : consultation et pilotage (2026-10-14)
- **Modèle** : aucune nouvelle racine d'agrégat. La fiche d'équipement, la disponibilité pour un patient, les indicateurs, la chronologie, les statistiques et les données du bon sont des **read models** de `contexts/gmao` (cas d'usage de lecture, ports `HistoriqueDesStatuts`, `LectureDesComptages`, `LectureDesCouts`, adaptateurs JPA : les sommes et comptages sont calculés par la base). Les trois calculs (`CalculDIndisponibilite`, `AnalyseDeDecision`, `IndicateursDIntervention`) sont des **services de domaine purs**, sans état ni Spring ; le seuil de réforme est un paramètre de l'application (`hemodialyse.gmao.reforme-seuil-ratio`, 0,60), pas une règle par centre (KB-GMAO-05).
- **Rendu du bon** : le module définit le port `ImpressionDuBon` (données du bon : intervention, équipement, intervenant, chronologie, instant d'édition) ; le moteur de documents, le modèle du centre et la mise en page restent dans `platform`, où `BonInterventionReportService` est l'adaptateur du port.
- **Direction** : le contexte Direction n'est pas extrait. Seule la **source** des chiffres GMAO migre, par deux lectures publiées dans `publishedlanguage/` : `SyntheseGmaoDuCentre` (synthèse d'un centre sur une période, avec l'analyse de chaque équipement) consommée par `DirectionGmaoQueryService`, et `GenerateursInstalles` consommée par `DirectionCapaciteQueryService`. L'endpoint, la garde de société, les alertes et la requête des patients sur équipement indisponible restent dans `platform` ; l'historique du centre est lu en un passage au lieu d'un par équipement.
- **Écarts décidés** (utilisateur, 2026-10-12, goldens `*_nouveau_code`) : KB-GMAO-69 (une intervention supprimée logiquement n'est plus lisible par identifiant : 400), KB-GMAO-72 (seuil comparé au ratio exact ; l'arrondi à 4 décimales n'est que l'affichage), KB-GMAO-73 (un équipement désactivé n'est plus disponible pour un patient). Reproduits : KB-GMAO-70 (GET du bon écrit la ligne de modèle de document), 71, 74 à 79, codes d'erreur, événement MODIFIEE parasite, seuil global.
- **Retiré** : les trois contrôleurs de suivi, de fiche et de statistiques, `InterventionSuiviQueryService`, `GmaoDecisionConfig`, les réponses JSON associées, `AideDecisionMaintenance` et `IndicateursIntervention` de `bc-gmao`. **Conservé** (temps 2) : l'équipement de `bc-gmao` (`GenerateurIndisponibleService`, `GmaoEvenementsPlanificationListener`, `PatientMigrator`) et les adaptateurs legacy encore semés par les fixtures de caractérisation G1 à G3 et par `ModelesDePersistanceAlignesIntegrationTest`.

## Amendement G6 temps 2 : retrait du module `bc-gmao` (2026-10-14)
- **Décision utilisateur** : le module `backend/bc-gmao` est supprimé (25 classes, 5 tests ; poms `backend`, `platform`, `bc-migration`, `Dockerfile`) dès que plus rien ne le référence et que tout est vert. C'est fait : plus aucune référence à `com.hemodialyse.backend.domain.gmao` hors du littéral des 3 erreurs 400 (parité).
- **Lecture de l'état des générateurs** : nouveau port publié `GenerateursDuCentre` (id, code, salle, statut, centre), distinct de `GenerateursInstalles` (non élargi). La reprise des patients le consomme par un port propre `GenerateursDeReprise` et une ACL (`GenerateursDeRepriseGmao`) ; `bc-migration` ne dépend plus de la GMAO. L'alerte « générateur indisponible » reçoit ses valeurs de l'événement du module.
- **Bugs** : KB-GMAO-80, 81, 82, 83 reproduits à l'identique (ADR 0019) ; correction à planifier après retrait.
- **Conséquence** : le contrôle d'alignement des modèles de persistance compare désormais chaque modèle du module à la description figée de sa table. Rien ne reste à retirer pour GMAO.
