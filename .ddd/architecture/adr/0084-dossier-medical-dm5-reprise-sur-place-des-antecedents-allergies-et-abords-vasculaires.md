# 0084 - Dossier médical, DM5 : reprise sur place (antécédents, allergies, abords vasculaires)

## À confirmer avec les métiers et le RGPD/DPO
Données de santé sensibles (diagnostics, allergies, accès vasculaires). Décisions prises par délégation, EN VIGUEUR mais À CONFIRMER. Détail : `known-bugs.md`, section « Décisions DM5 ».

**Reproduit, à confirmer** : (KB-MED-60) un antécédent, une allergie inconnus, d'un autre patient ou d'un autre centre = 400 `BAD_REQUEST` à la correction et à la résolution (pas 404) ; DELETE = 204 même sans effet ; (KB-MED-63) le type d'abord est un texte libre (vide accepté), la Planification n'exige la compétence CATHETER que pour `KT_AIGU` et `KT_TUNNELISE` en majuscules, abord actif et non terminé (RG-PLN-097, NON modifiée) ; aucune cohérence « actif » / date de fin ; aucune limite de date ; (KB-MED-64) diagnostic CIM10, LOINC, ATC ou LOCAL, simple contrôle de forme, unicité applicative du diagnostic actif seulement (aucune contrainte en base, verrou consultatif sans migration), jamais pour un libellé libre ; (KB-MED-65) correction destructrice (champs absents effacés, type ignoré, RESOLU sans fin, réouverture, pas de contrôle du futur), résolution sans date ou future acceptée ; (KB-MED-66) allergie REFUTEE reste « critique » si la criticité est HAUTE, aucune unicité, BASSE efface les manifestations ; (KB-MED-67) événements `AntecedentAjoute`, `AntecedentResolu`, `AllergieDeclaree`, `AllergieCritiqueDeclaree` jamais publiés : RIEN inventé ; (KB-MED-68) audit pauvre (`PATIENTS_*` sans action métier), lectures non tracées, aucun audit nouveau ; (KB-MED-69) droits : antécédents et allergies lus par MEDECIN et ADMIN, écrits par MEDECIN, l'INFIRMIER refusé y compris sur `critiques` mais autorisé à LIRE les abords ; (KB-MED-70) codes FHIR d'allergie inventés dans le système `condition-clinical` : FHIR est DM8, NON modifié ; (KB-MED-71) bornes de pagination (page négative = 0, taille nulle ou négative = 20, plafond 200), lectures d'un patient inconnu = 200 vide ; abord : `actif` absent = actif et la date d'enregistrement (`created_at`, rendue comme `updatedAt`) est réécrite à chaque PUT (résidu de KB-MED-62).

## Contexte
Le filet DM5 (51 scénarios, 51 goldens, KB-MED-58 à 71) est vert sur le legacy depuis 531ae309. Trois contrôleurs (`AntecedentRestController`, `AllergieRestController`, `AbordVasculaireRestController`, 14 routes), tables réelles `antecedents_medicaux`, `allergies_patient`, `abords_vasculaires` ; les schémas parallèles gelés `antecedents` / `allergies` du module (GEL.md, ADR 0072) ne sont ni lus ni écrits. Les abords vasculaires sont rattachés à DM5 par délégation (à confirmer). Lecteurs : FHIR (`Condition`, `AllergyIntolerance`, `Procedure`), Planification (`ContraintesDesPatientsJdbc`, SQL), `GreffePdfService` (antécédents), import et rollback d'historique.

## Décision
1. **Reprise SUR PLACE** : `AntecedentsControleur`, `AllergiesControleur`, `AbordsVasculairesControleur` servent les MÊMES URL, champs JSON et rôles ; mêmes tables, aucune colonne ni contrainte ajoutée ; pas de façade, de flag ni de projection.
2. **Agrégats** à une seule entité, `UUID` généré par le port `GenerateurDIdentifiants` : `Antecedent` (type, `CodeClinique`, libellé libre, période, statut `ACTIF|RESOLU|INACTIF`, intentions `enregistrer`, `corriger`, `resoudre`), `Allergie` (`CodeClinique` de substance, catégorie, criticité, type de réaction, manifestations, statut, intentions `declarer`, `corriger`), `AbordVasculaire` (intentions `enregistrer`, `remplacer`). Objet-valeur `CodeClinique` (système, code normalisé, affichage). Listes fermées (`TypeDAntecedent`, `StatutClinique`, `SystemeDeCodage`, `CategorieDAllergie`, `CriticiteDAllergie`, `TypeDeReaction`, `StatutDeVerification`) lues par `lire` : 400 sans nom interne.
3. **Ports** : `Antecedents`, `Allergies`, `AbordsVasculaires` (domaine), `PatientsDuCentre` (ACL Patient et couverture, existant), `UniteDeTravail` (lock_timeout 5 s), `HorlogeDuCentre` (bean `horlogeDesFichesCliniques`, jour UTC = jour de la JVM comme le legacy : date par défaut d'une allergie, limite « futur »), `SessionCourante`, `GenerateurDIdentifiants`. Adapters JDBC `AntecedentsJdbc`, `AllergiesJdbc`, `AbordsVasculairesJdbc` (verrous communs `VerrousJdbc`). Le double en mémoire, H2 et PostgreSQL 16 passent le MÊME contrat par port.
4. **Écarts décidés** (32 goldens `_nouveau_code`, legacy archivé octet pour octet depuis 531ae309 dans `characterization/dossiermedical/dm5/{antecedents,allergies,abords}/_ecarts-legacy/<dossier>/<scénario>__<nom>.legacy.json`, approuvés un par un : lecture du fichier reçu, relecture du diff, écriture, rejeu de la classe) :
   - **KB-MED-58** : corps absent, illisible, tableau, `{}`, énumération ou type absent, code sans système, `actif` ou dates illisibles, `centerId`, identifiants, pagination illisibles : **400 stable** (avant : 500) ; un profil sans droit reçoit **403 AVANT 400** (mécanisme `ErreursDuDossierMedicalAdvice`, étendu aux trois contrôleurs) ;
   - **KB-MED-59** : plus de nom d'énumération interne dans les 400 (type, système, statut, catégorie, criticité, type de réaction, statut de vérification) ;
   - **KB-MED-61** (trou de sécurité) : patient inconnu ou d'un autre centre = **404 `PATIENT_INTROUVABLE`** à l'écriture (ACL `PatientsDuCentre`), plus de ligne orpheline ni d'écriture croisée entre centres ; lectures : 200 liste vide, comme DM3 et DM4 ;
   - **KB-MED-62** (trou de sécurité) : le PUT d'un abord n'est plus un « enregistrer » : identifiant inconnu, abord d'un autre patient ou d'un autre centre = **404 `ABORD_VASCULAIRE_INTROUVABLE`** ; jamais créé ni réaffecté ni écrasé ;
   - **Bornes de colonne = 400** (avant : 500 `DATA_ACCESS_ERROR`) : sévérité 50, libellé 255, affichage du code 255, code 20 ; abord : type 20, côté 10, localisation 255, complications 500 ;
   - **Verrous = 409** : ordre global **centre (Planification), fiches (`SELECT ... FOR UPDATE`), `app_user`, verrous consultatifs** ; `lock_timeout` 5 s ; `ANTECEDENT_ECRITURE_CONCURRENTE` (fiche, ou diagnostic à l'enregistrement et à la correction), `ALLERGIE_ECRITURE_CONCURRENTE`, `ABORD_VASCULAIRE_ECRITURE_CONCURRENTE` ; les enregistrements simultanés du même diagnostic actif se suivent (verrou consultatif de transaction sur PostgreSQL, aucune migration) ;
   - **DELETE sans effet** : reste 204 mais n'est plus inscrit au journal d'audit (attribut `hemodialyse.audit.sansTrace`, déjà géré par `AuditRequestFilter` depuis DM4 : aucune édition de la plateforme) ;
   - **Ordre déterministe** (KB-MED-71, invisible aux goldens H2) : départage par création puis identifiant ; les abords SANS date en dernier sur tous les SGBD (PostgreSQL les plaçait en tête, `NULLS LAST` explicite) ;
   - **Lecture normalisée comme le legacy** : un code relu de la base est rendu en majuscules (le legacy repassait par `ConceptCode.of`) mais n'est plus revalidé ; une ligne dont l'énumération ou le système est illisible en base est **ignorée** par toutes les lectures (avant : 500 pour toute la liste), journalisée en WARN avec son identifiant SEUL, figée par les contrats JDBC ; elle ne peut plus être corrigée ni supprimée par le module (limite consignée, repérage SELECT seule : `verifications-production.md` §49 ; la correction des données se décide avec les métiers).
5. **Comportement vu par la Planification et FHIR IDENTIQUE** : `abords_vasculaires` garde le format des lignes lu par `ContraintesDesPatientsJdbc` (types libres, `actif`, `date_fin`) ; le filet `LesAbordsVasculairesEtLaPlanification…` (13 profils, 3 jours, effet de chaque écriture HTTP) est inchangé, 2/2 vert. Les goldens FHIR de DM5 (`Condition`, `AllergyIntolerance`, `Procedure`) sont inchangés. **Aucun golden hors DM5 modifié.** Un seul résidu : `created_at` d'un abord est réécrit à chaque PUT (reproduit), la Planification ne le lit pas.
   **Divergence d'ordre sur PostgreSQL (consignée)** : le module liste les abords sans date en DERNIER (`NULLS LAST`), alors que l'export FHIR `Procedure` (lecteur JPA conservé, `findByPatientIdAndCenterIdOrderByDateCreationDesc`) les place en TÊTE sur PostgreSQL (en dernier sur H2, seul rejoué par les goldens, qui trient d'ailleurs l'export par type). Le « comportement FHIR identique » vaut donc pour le contenu et sur H2, pas pour l'ordre des abords sans date sur PostgreSQL. L'ordre sera aligné au moment de DM8 (FHIR), avec les décisions sur les codes FHIR.
   **Sort des lignes illisibles** : elles restent « ignorées + WARN » (identifiant seul, émis seulement quand une ligne est effectivement écartée : une requête de comptage combinée par lecture, le repérage des identifiants n'a lieu que si un écart existe) ; elles se repèrent par la requête 6 de `verifications-production.md` §49 ; la décision de nettoyage (corriger, supprimer, migrer) appartient aux métiers et au DBA AVANT DM7, aucune correction automatique.
   **Verrous consultatifs** : l'espace de clés de `hashtextextended` est partagé entre contextes et fiches ; il est rendu disjoint par des préfixes littéraux (`antecedent|centre|patient|système|code`, `serologie|…`, etc.) ; tout nouveau verrou consultatif doit porter son propre préfixe.
   **Liste nominative de retrait de la revue du 2026-12-15** (méthodes et classes mortes depuis DM5) : `Antecedent.creer`, `modifier`, `resoudre`, `pullEvents` et `AntecedentEvent` ; `Allergie.declarer`, `modifier`, `pullEvents` et `AllergieEvent` ; `AntecedentRepositoryPort.save`, `deleteById`, `findPagedByPatientId`, `findById` ; `AllergieRepositoryPort.save`, `deleteById`, `findPagedByPatientId`, `findById` ; `AbordVasculaireRepositoryPort.save`, `deleteById`, `findPagedByPatientId` ; leurs implémentations dans `AntecedentRepositoryAdapter`, `AllergieRepositoryAdapter`, `AbordVasculaireRepositoryAdapter` et les méthodes dérivées des trois `*JpaRepository` correspondantes ; ne resteront que les lectures `findByPatientId` (FHIR, `GreffePdfService`) tant que DM7 et DM8 ne les reprennent pas. Aucune garde supplémentaire : `TableDuDossierMedicalTest` reste `@Disabled` (module gelé).
6. **Legacy retiré** (seams.md, `seamAllowed` vide) : trois contrôleurs, huit DTO, `AntecedentUseCase`, `AntecedentDomainService`, `AntecedentDupliqueSpecification`, `AllergieUseCase`, `AllergieDomainService`, `AbordVasculaireUseCase`, `AbordVasculaireDomainService`, quatre tests, trois beans de `DomainServiceConfig`, dix-neuf entrées mortes de `covered.json`. **Conservés** (lecteurs FHIR, PDF de greffe, import, rollback) : agrégats legacy `Antecedent`, `Allergie`, `AbordVasculaire` et leurs événements, ports `*RepositoryPort`, énumérations, `ConceptCode` / `CodingSystem` / `PeriodeClinique`, adapters, entités et dépôts JPA. **Jalon de retrait : à la fin de DM7 (PDF de greffe) et DM8 (FHIR), revue au plus tard le 2026-12-15** (comme DM3 et DM4). Les méthodes d'écriture de ces résidus (`creer`, `modifier`, `resoudre`, `declarer`, `pullEvents`, `save`, `deleteById`) sont mortes.

## Documentation fonctionnelle non régénérée (justification)
Aucun écran, texte, URL, champ ni rôle ne change (aucun frontend modifié ; le PUT d'un abord vise toujours un abord existant). Les effets visibles sont des 400/403/404/409 à la place de 500 ou d'un enregistrement croisé pour des entrées illisibles ou hors périmètre. Les règles de gestion sont à jour dans `docs/reference/regles-de-gestion/11-dossier-medical.md` (RG-MED-035 à 037, garde `ReglesDeGestionDocumentationTest`) ; la documentation fonctionnelle et la maquette ne décrivent pas ces cas.

## Questions ouvertes
Rattachement des abords à DM5 ; bandeau d'allergies critiques pour l'infirmier ; statut REFUTEE dans le bandeau ; liste fermée de types d'abord partagée avec la Planification ; unicité des allergies ; publication d'événements (allergie critique) ; audit des lectures et actions métier (DPO) ; contrainte unique du diagnostic actif en base après nettoyage ; codes FHIR d'allergie (DM8) ; `created_at` réécrit à chaque PUT d'abord ; jour du centre.

## Conséquences
- Preuves : filet DM5 51/51 vert sur le nouveau code (19 inchangés, 32 `_nouveau_code`), 140 tests nouveaux du module (52 antécédents, 45 allergies, 43 abords : domaine, application avec fakes, contrat par port sur double, H2 et PostgreSQL 16 jetable `backend/scripts/dossier-medical-dm5-pg16-rejeu.sh`, verrou de ligne et verrou de diagnostic à deux connexions, advice 409/400/403/404), `check-arch.ts` 0 violation, ArchUnit du module, `FrontieresDesContextesTest`.
- Transaction : chaque cas d'usage n'écrit qu'UNE fiche (un agrégat, une transaction) : pas de test de transaction multi-écritures (contrairement à DM4 qui réévalue la Planification).
